# Balanced routing with passive usage

`routing.strategy: balanced` uses the same score as our Claude account launcher and Conveyor. For each quota window, it divides remaining capacity by time until reset and active session load. Plan weights express capacity ratios; a 20x/5x pool can use 4/4/1. Weekly capacity supplies the base score. A short-window score below 0.5 applies a penalty. Observations older than one hour project usage forward from the observed burn rate. Elapsed resets become unknown fresh windows rather than permanently exhausted accounts.

Session affinity wraps balanced selection. Healthy existing bindings keep their credential. New conversations and genuine failover receive the best available score. The existing provider/model availability, priority and cooldown filters still apply. Concurrent requests from one logical session count as one busy slot per credential. New selections and reservations are atomic; slots release on completion, errors and cancellation. Providers without passive quota windows use weight and load. Home mode retains Home-owned dispatch.

Quota is observed from the existing Claude unified headers, Codex HTTP headers and Codex SSE/websocket events. Partial responses preserve the newest observation of each duration. Codex primary/secondary windows are classified by duration and relative resets are anchored to observation time. Additional model-specific Codex limits are not treated as global pool limits. Generic providers can supply normalized `windows` metadata. Claude credentials can point `windows_file` at the existing local Claude/Conveyor JSON report. Missing observations remain unknown; no usage request is issued.

`GET /usage` returns token-free local snapshots and scores. `/dashboard` displays them and reads only that local endpoint. The proxy API key policy also applies to `/usage`; an empty access key list permits an unauthenticated tailnet deployment. Management credentials, OAuth import and arbitrary API-call routes remain disabled when no management secret is configured. Bind to the host's Tailscale address, not all interfaces.

# Claude proxy-only mode

Set `upstream.claude.proxy-only: true` for native Claude Code/Agent SDK clients. Claude credentials must be locally imported setup-tokens with `is_setup_token: true`, `machine_device_id` from the exit node's native Claude profile, and optional `setup_account_uuid` from that profile. A cached native account UUID is preserved; a profile without one uses an empty UUID. The proxy never resolves it through a profile endpoint.

This path forwards the native business payload and stream bytes. It does not cloak, normalize thinking/sampling/cache TTLs, repair signatures, rename tools or inject prompts, cache markers or diagnostics. It substitutes the selected token, replaces native user identity with the configured machine identity, resolves the routed model, applies explicitly configured payload rules once and re-signs an existing CCH block. It does not create a missing billing block. Session and parent identity survive. Caller software versions, betas and other headers survive; configured OS/architecture describe the exit machine. HTTP connection framing is rebuilt by the transport.

Claude background refresh, profile lookup, OAuth login, quota probes, management API calls using Claude credentials and generic executor HTTP calls are blocked. Count-token requests are proxied only when received from the client. Codex retains its normal OAuth renewal. The service should use `--local-model` and disable the downloaded management panel so local model/dashboard reads need no catalog or panel fetch.

Tests include a sanitized request shape captured from Claude Code 2.1.285 on Jetson with a dummy setup-token and mock upstream, native request/SSE preservation, permitted identity/CCH changes, no auxiliary Claude calls, balanced/affinity selection, generic providers, passive Codex SSE with logging disabled, parallel reservations and stream cancellation. The fixture replaces native system prose and identity with test values. It verifies request semantics and application headers, not byte-for-byte TCP/TLS equivalence or a provider's internal account/cache policy.
